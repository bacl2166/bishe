# 扩展预处理与约束样本审计

原 v2 乐器域审计有 200 位测试用户、800 条请求，但无筛选条件仅 45 位用户的正例落入目录；价格约束有 9 位有效用户，品牌、类别和交叉约束为 0。扩大目录和独立用户样本有助于增加观察机会，但不能保证稀有品牌或交叉筛选拥有足够历史正例。

## 扩展配置

`configs/expanded/` 提供三域的实验一、二配置，使用 `scripts/run_suite.py --config-dir configs/expanded` 选择，原小规模配置保留。

| 参数 | 小规模 v2 | 扩展配置 |
|---|---:|---:|
| 训练目录上限 | 3000 | 10000 |
| 有测试事件的用户上限 | 200 | 2000 |
| 请求上限，含配对随机对照 | 800 | 20000 |
| 单用户训练历史上限 | 50 | 50 |
| 最小训练历史 | 5 | 5 |
| 目录商品最少训练交互 | 5 | 5 |
| 推荐模型训练前缀上限 | 50000 | 50000 |
| 实验二固定诊断请求上限 | 80 | 200 |

训练截止、验证/测试时间边界、请求种子、三组编码/模型种子、全部编码和约束定义保持不变。目录仍仅按训练交互选择，用户仍仅按训练历史资格、测试事件存在和固定哈希选择；不要求正例落入目录或满足筛选。原始完整文件可复用。新输出为 `runs/<domain>-experiment1-expanded` 与 `runs/<domain>-experiment2-expanded`，后者明确引用前者。

请求分配先覆盖无筛选基线，再轮转结构模板并保留随机对照配对。若达到 2000 位用户，20000 条预算可覆盖 2000 条基线及 9000 组结构/随机配对；一个用户会贡献多个请求，统计始终需要按独立用户计算。

这些是上限，不代表每域必定达到；也不保证扩大目录后抽中的新用户具有更高目录覆盖率。三域按相同上限处理，实际差异报告到审计中。

## 先准备，再审计

更新代码、复用已下载的完整文件，在仓库根目录执行：

```bash
CUDA_VISIBLE_DEVICES="" python -u scripts/run_suite.py \
  --config-dir configs/expanded --experiment 1 --datasets musical \
  --prepare-only --resume

CUDA_VISIBLE_DEVICES="" python -m exp1.audit \
  --run runs/musical-experiment1-expanded --split validation
```

两个步骤均不训练模型，审计模块仅用标准库。预处理仍需要安装项目依赖以记录运行环境。数据扫描、JSON 序列化与规则匹配会消耗 CPU、内存、磁盘和时间；用 `du -sh data runs`、`df -h .`、`free -h` 实测占用。已有源文件与旧运行目录均不删除。代码指纹变化后，旧结果若需原样续跑，应使用其对应提交；不能把不同版本的冻结结果拼入新实验。

其他域在完整文件已下载后，可将 `--datasets` 换为 `fashion appliances`。每域分别审计，不要求所有域拥有相同属性覆盖。

## 审计表如何读

`python -m exp1.audit` 默认使用验证标签，在冻结目录和用户集合上重新构造同规则请求，只写独立的 `constraint-support-validation.json/csv`，不覆盖原 `prepared.json`、`audit.json` 或 `requests.json`。由于入选者须有测试事件，验证审计覆盖这些入选者中实际存在验证事件的人；验证人数可能少于测试人数，不得混淆。已保存的正式请求仍是测试请求。

分组键为 `family / strength / variant / matched_family`。随机对照按其对应结构约束族分别统计，避免混合不同来源。每行包括：

- 请求数与独立用户数。
- 正例目录内用户数、正例可行请求数和独立用户数。
- 非空候选用户数、空集合比例、候选数均值/中位数/最小值/最大值。
- 推荐和机制指标的样本数量提示。

默认数量检查线为每个分组至少 100 位用户和 30 位有效正例用户，可用 `--min-users` 与 `--min-positive-users` 显式调整。这只是规划参考，**不是统计功效证明或论文显著性保证**，也不会据此删除用户、请求或约束。标签不参与请求抽样。

`recommendation_support` 有三种值：

| 值 | 含义 |
|---|---|
| `no_feasible_positive` | 没有有效正例，HR/NDCG没有可用分母 |
| `limited` | 有有效正例，但至少一项数量检查线未达到 |
| `meets_planning_count` | 达到所设数量检查线，仍需正式统计分析 |

`mechanism_support` 仅按非空候选请求中的独立用户数量提示。没有可行历史正例的请求仍可能用于 OracleRecall 与搜索分数损失；空可行集合另行统计。

若品牌、类别或交叉条件仍为 0，须报告该结果。不要持续查看测试正例来调整品牌、阈值、种子或入选用户。验证阶段若显示该全局筛选协议缺乏推荐质量标签支持，可另行预先设计基于训练历史的购物筛选协议，并独立评估；它与本次纯规模扩展不同，不能混入同一对照。

测试审计在配置冻结后运行：

```bash
CUDA_VISIBLE_DEVICES="" python -m exp1.audit \
  --run runs/musical-experiment1-expanded --split test
```

## 后续模型运行

扩展配置也保留了模型运行入口，但本轮首先只运行准备和审计。20000 请求若直接套用全部编码、种子、模式和预算，实验一单域上限为 `20000×12×3×3×3×3×6=116640000` 行，逐请求输出及计算成本将显著扩大，不能根据旧版 800 请求推断总耗时和磁盘需求。正式评测的请求预算、编码组合、诊断量与重复次数应根据验证阶段的样本支持和实测成本预先固定，然后在独立输出目录生成对应配置和测试请求。不能按测试命中情况挑选请求。
